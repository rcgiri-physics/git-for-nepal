# 1. Issues as a to-do list

## Hook
A team of four says 'we'll just remember what to do'. Two weeks later, three people did the same thing.

## Concept (unplugged or visual first)
An **issue** is a task written where everyone can see it. Good issue = a short title (verb first), what/why, and how we will know it is done. Practise on paper sticky notes first (a kanban wall: To do / Doing / Done).

## PRIMM lab
1. In your team's repo (LAN server or hosting platform), open the Issues page.
2. **Predict:** which of these is a good issue — 'fix it', 'Add contact form to the school website', 'website bad'?
3. Write 5 issues for the School Website project. **Modify** them after a neighbour's feedback.
4. Label (`bug`, `feature`, `docs`) and assign each issue to one person.
5. **Make:** put them on a board; agree the first three to do.

## Parsons practice
Order the life of an issue: *open · discuss · assign · work on a branch · close with a commit message that mentions it*.

## Exit ticket
1. What three parts make a good issue?
2. Who should an issue be assigned to?
3. *Misconception:* 'issues are only for bugs.' True or false?

## Teacher notes
Tier 0/1 teams use a paper kanban wall. Keep titles in English or Nepali but code names in English. Rubric: clear title, why, done-check.
